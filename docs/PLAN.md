## 2. 阶段门禁规则

### 通用规则

1. **阶段授权**：逐阶段模式下，每个阶段开始前都要拿到用户当次确认；**连续实施模式下，启动语里的一次授权即可覆盖全部必做阶段**（见 `AGENTS.md` §5）；
2. 只做当前阶段列出的工作项。发现范围外的问题 → **记进汇报，不要顺手做**；
3. 阶段结束 → 跑验收 → 更新 `CHANGELOG.md` → **逐阶段模式停下等确认；连续模式立即进入下一阶段**，但仍须输出四段汇报；
4. 同一问题连续两次未通过验收 → 停下汇报，不要无限重试；
5. 任何阶段中需要触碰红线或灰名单 → 立即停下（`AGENTS.md` §4）；
6. **硬停点见 `AGENTS.md` §5——连续实施模式不豁免其中任何一条。**

### 每次汇报必须包含四段

```
1. 做了什么        （具体改动 + 文件清单）
2. 验证了什么      （跑了什么命令、结果如何——必须区分「源码确认」与「实机验证」）
3. 没验证什么      （明确列出遗留的未验证项）
4. 下一步          （建议动作 + 需要用户决策的点）
```

## 5. P2 — 门禁 + 设置 UI

### 进入条件

P1 退出条件满足，且用户确认。

### 工作项 A：门禁核心

> 规格见 `SPEC.md` F3；字段语义与参数参考 `RESEARCH.md` §5.5（dsh-bridge）。

1. `src/auth/manager.ts`：PBKDF2-SHA256（迭代 `600000`、派生 32 字节、存储格式 `pbkdf2-sha256$<iterations>$<hex>`、兼容旧裸 hex 按 10000 次）、**双密码**（访问密码 + 独立管理密码）、`secretToken` 生成与校验、会话签发与校验、IP 失败计数与锁定、`timingSafeEqual` 比较、统一 `verifyRequest()` 入口（HTTP 与 WS 共用）、`adminPolicy` 与 `allowLoopback` 判定；
2. `src/store/secrets.ts`：敏感数据（哈希与盐、`secretToken`、会话）持久化到 `<dataDir>`，文件权限 600；**普通会话落盘、管理员会话仅内存**；
3. `src/store/preferences.ts`：非敏感配置持久化 + 已知键白名单校验（未知键一律丢弃）；
4. `src/auth/login-page.ts`：登录页（HTML + 内联 CSS，**必须区分**密码错误 / 已锁定 / 尚未设置密码三态）；
5. 把门禁接进 HTTP 与 WS 两条路径：未认证 → HTML 请求给登录页 / `/api/*` 给 401 JSON / upgrade 直接拒绝；
6. 管理解锁端点：**必须豁免访问会话校验**（否则访问会话失效后管理入口永远解不开——dsh-bridge 的死锁教训）；
7. `GET /plugins/dsh-lan-guard/auth-status` 脱敏端点（绝不暴露 `secretToken` 或哈希）；
8. CSRF 校验（`Origin` / `Sec-Fetch-Site`）。

### 工作项 B：设置 UI（混合路线「乙」）

> 规格见 `SPEC.md` F6；做法参考 `RESEARCH.md` §5.6（dsh-notify）与 §4.1（官方 `configForms`）。

9. `src/config.ts`：把非敏感开关（`enabled` / `mode` / `adminPolicy` / `adminProtection` / `allowLoopback`）声明为插件 `Config` 的 **volatile** 字段——编辑提交进运行引用、不重挂插件；官方 `configForms` 会自动为它们生成表单；
10. `src/settings/routes.ts`：`/plugins/dsh-lan-guard/config` 端点，**必须先用 `connection.requestRejection(req)`** 复用 DSH 原生栅栏，非 GET 再校验同源；**必须保留这条自定义通道**——官方表单在非回环页面（手机经代理访问）只读，见 `RESEARCH.md` §4.1；
11. `src/client.ts`：注册官方 `settings.section` seat（`id: 'dsh-lan-guard'`、`order: 100`、`label: '局域网访问'`）；纯 `React.createElement`，**不引入 JSX**；内联 CSS 使用官方变量 `--dsw-alias-*`；覆盖 `(hover:none) and (pointer:coarse)` 与 `max-width:620px` 两个响应式断点；
12. `package.json` 的 `dsh.client.inject` 声明 `dsh-client-ui-renderer`、`dsh-client-ui-layout`、`dsh-client-ui-settings`、`dsh-client-ui-settings-general`。

### 必须验证

**门禁**：

- [x] 未认证访问 → 登录页；`/api/*` → 401 JSON；
- [x] 未认证 WebSocket upgrade → 被拒绝；

## 8. 工作量与风险提示

| 阶段 | 预计代码量 | 主要风险 |
| --- | --- | --- |
| P1 | 300–400 行 | 上游 cookie 路线 A 的 token→cookie 交换细节（303 + Set-Cookie 处理）；document-relative 路由与尾斜杠规范化 |
| P2 | 550–750 行 | 门禁与 WS upgrade 的衔接顺序；持久化并发写；设置页与 DSH 原生栅栏的衔接；混合路线下 volatile `Config` 与自定义端点的分工 |
| P3 | 350–500 行 | 证书与网卡 IP 的绑定；手机信任自签 CA 的操作体验；二维码刷新时机与免密链接的凭据保护 |

**整体判断**：P1+P2+P3 合计约 **1200–1650 行**。其中证书、门禁、设置 UI、二维码四块都有成熟实现可借鉴参数与模式（`RESEARCH.md` §5.1 / §5.5 / §5.6 / §5.8），TS 工程栈可照 §5.9 模板搭建；真正需要自己设计的只有反代 + 头改写 + cookie 注入那一小块。
