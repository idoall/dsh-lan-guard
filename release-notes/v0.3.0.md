<h3 id="cn-v0.3.0">中文</h3>

### 版本对应

仍针对 **DeepSeek Harness `0.1.7-rc.1`**，声明范围不变（`>=0.1.7-rc.1 <0.2.0`）。**DSH 侧没有变化，不需要适配。**

### 为什么必须适配

**不需要适配**。这是一次功能版本：新增「设备批准与永久拉黑」，并修掉一个会让分享出去的链接**打开后页面空白**的门禁缺陷，另有两处设备列表的排版修复。安装形态、配置键与磁盘格式都没有破坏性变化。

### 改了什么

1. **新增：设备批准与永久拉黑（SPEC F9）**
   - 新增开关 `auth.requireApproval`（默认 **false**＝保持现状）：打开后，新设备完成命名会进入「**待批准**」，需管理员在设置页点「批准」才能访问；
   - 设备状态三态 **`pending` / `approved` / `blocked`**；F9 之前写入的设备记录在加载时**自动迁移为 `approved`**，不会打断既有设备；
   - **「吊销并拉黑」是永久的**：被拉黑的设备即使知道访问密码、换浏览器重新配对也会被拒绝，唯一出路是管理员「**解除拉黑**」——刻意不使用设备指纹（换浏览器/升级系统就会失效），由人决定且决定持久；
   - 设置页「已授权设备」新增**三组列表**（待批准：批准 / 拒绝并拉黑；已授权：吊销并拉黑；已拉黑：解除拉黑）+ 待批准提醒条；
   - 新增端点动作 `approve` / `block` / `unblock`，沿用既有管理面鉴权、CSRF 与远程只读规则。
2. **修复：分享出去的链接打开后页面空白（HTML 200，插件资源 428）**
   - 根因：门禁里两处「已认证」分支直接放行，**跳过了设备命名检查**——应用 HTML 被送出，而它随后请求的插件资源被以 `428 pairing_required` 拒绝，页面因此一片空白；
   - 现在所有已认证入口统一走同一个检查：带 `?auth=` 打开会先看到**配对页**，命名拿到设备身份后资源才放行。
3. **改进：免密链接在「仅密码」模式下无效时给出明确提示**（原先只落到一个没有解释的登录页）。
4. **修复：设备列表排版**——小号按钮不再折行；每行固定为「名称 + 状态芯片（间隔 5px）……操作按钮贴最右」+「创建/最近使用/来源」两行，长设备名以省略号截断而不会挤走按钮。

### 谁受影响

- **从 0.2.0 升级的人**：默认行为不变（新开关默认关闭）；想用「永久拉黑」再打开它；
- **分享过 `?auth=` 链接的人**：本次修掉了「打开是空白页」的缺陷，链接现在会正常走到配对页；
- **设备列表看起来不一致的人**：行高与按钮位置已固定；
- 不安装本插件的人：不受影响。

### 兼容性与升级

- 与 DSH `0.1.7-rc.1` 配套；`peerDependencies` 与 `engines` 未变；
- **升级无需任何操作**：配置、密钥、设备配对记录与 CA 全部沿用；既有设备记录在加载时自动补上状态字段（视为已批准）；
- 回滚到 0.2.0 同样安全（新增字段会被忽略）。

### 限制

- 「永久拉黑」不依赖设备指纹：它靠「新设备需要管理员批准 + 拉黑名单」，因此**重新放行必须由管理员手动操作**——这是刻意的取舍（指纹会因换浏览器/升级系统而失效，不可靠）；
- 「新设备需要管理员批准」默认关闭；开启后每台新设备都需要你点一次「批准」；
- 其余限制与 0.2.x 相同（自签 CA 需每台设备信任一次；mDNS 默认关闭且手机浏览器基本用不上，二维码才是主路径；远程默认只读；局域网明文 HTTP 需显式确认风险；访问密码是共享的；不提供公网隧道 / IM Bot / 端口转发）。

<h3 id="en-v0.3.0">English</h3>

### Version correspondence

Still built for **DeepSeek Harness `0.1.7-rc.1`** with the same declared range (`>=0.1.7-rc.1 <0.2.0`). **Nothing changed on the DSH side, so no adaptation is needed.**

### Why this release exists

**No adaptation was required.** This is a feature release: it adds device approval with a permanent ban, fixes a gate defect that made a shared link open a **blank page**, and fixes two layout problems in the device list. The install shape, configuration keys and on-disk format have no breaking change.

### What changed

1. **New: device approval and permanent ban (SPEC F9)**
   - New switch `auth.requireApproval` (default **false**, i.e. unchanged behaviour): when on, a newly named device lands in **pending** and needs an operator's approval in the settings page;
   - Three device states — **`pending` / `approved` / `blocked`**; records written before F9 are **migrated to `approved` on load**, so existing devices keep working;
   - **"Revoke and block" is permanent**: a blocked device is refused even if it knows the access password and re-pairs from another browser; the only way back is the operator's **"unblock"**. Device fingerprinting is deliberately not used (it breaks when the browser or OS changes) — a human decides, and the decision sticks;
   - The "authorised devices" tab gains **three lists** (pending: approve / deny-and-block; approved: revoke-and-block; blocked: unblock) plus a pending-approval banner;
   - New endpoint actions `approve` / `block` / `unblock`, reusing the existing management authentication, CSRF checks and remote read-only rule.
2. **Fixed: a shared link opened a blank page (HTML 200, plugin assets 428)**
   - Root cause: two "already authenticated" branches in the gate returned early, **skipping the device-naming check** — the app HTML was delivered while the plugin assets it then requested were refused with `428 pairing_required`, leaving a blank page;
   - Every authenticated entry point now goes through the same check: opening with `?auth=` shows the **pairing page** first, and assets are released once the device has an identity.
3. **Improved: an inert passwordless link in "password only" mode now says so** (it previously dropped the visitor on an unexplained login page).
4. **Fixed: device list layout** — small buttons no longer wrap; every row is now "name + status chip (5px apart) … action button pinned right" plus a "created / last used / source" line, and a long device name is ellipsised instead of pushing the button away.

### Who is affected

- **Anyone upgrading from 0.2.0**: behaviour is unchanged by default (the new switch is off); turn it on to get the permanent ban;
- **Anyone who shared a `?auth=` link**: the blank-page defect is fixed — the link now reaches the pairing page;
- **Anyone who found the device list inconsistent**: row heights and button placement are now stable;
- People who do not install this plugin: unaffected.

### Compatibility and upgrading

- Matches DSH `0.1.7-rc.1`; `peerDependencies` and `engines` are unchanged;
- **Upgrading needs no action**: configuration, secrets, paired devices and the CA all carry over; existing device records get their state field filled in on load (treated as approved);
- Rolling back to 0.2.0 is equally safe (the added field is simply ignored).

### Limitations

- The permanent ban does not rely on device fingerprinting: it works through "new devices need operator approval" plus a block list, so **re-admitting a device is always a manual operator action** — a deliberate trade-off (fingerprints break when the browser or OS changes);
- "New devices need operator approval" is off by default; when enabled, every new device needs one click from you;
- All other limitations are unchanged from 0.2.x (the self-signed CA must be trusted once per device; mDNS is off by default and phone browsers rarely use it, the QR code is the reliable path; remote access is read-only by default; LAN plain HTTP requires an explicit risk acknowledgement; the access password is shared; no public tunnels, IM bots or port forwarding).
