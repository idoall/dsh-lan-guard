<h3 id="cn-v0.3.1">中文</h3>

### 版本对应

本版本针对 **DeepSeek Harness `0.1.7-rc.2`** 验证通过，同时仍兼容 `0.1.7-rc.1`。声明范围保持 `>=0.1.7-rc.1 <0.2.0` 不变。

### 为什么必须适配

DSH 从 `0.1.7-rc.1` 升到 `0.1.7-rc.2` 后，我们按 `docs/RESEARCH.md` §8 的复核清单逐项核对，结论是：**本插件依赖的宿主/客户端接口全部存在且未变，不需要任何源码改动**——所以这一版是**验证版**（零代码改动），只更新兼容元数据与文档，让使用者在 npm 上能看到「这个插件已针对 rc.2 验证」。

### 改了什么

- `dsh.compatibility.dshReleases` 增加 **`0.1.7-rc.2: compatible`**（保留 `0.1.7-rc.1`）；
- **README 中英双语兼容表重写**：补上 `0.1.0 → 0.3.1` 的完整「插件版本 ↔ DSH 版本」对应历史，并把「当前已验证的最新 DSH 版本」更新为 **`0.1.7-rc.2`**，同时写明本次的验证方式（逐个接口核对 + 端到端跑通）；
- `docs/RESEARCH.md` 新增 §8.9 记录 rc.2 复核结果；
- **运行代码零改动**：门禁、代理、自签 TLS、设备配对与批准、设置页、升级检测全部与 `0.3.0` 相同。

### 谁受影响

- 升级到 **DSH `0.1.7-rc.2`** 的人：可以放心使用本插件，接口未变、无需配置迁移；
- 仍在使用 `0.1.7-rc.1` 的人：**无需升级插件**，`0.3.0` 继续可用；
- 新装用户：`@latest` 会拿到 `0.3.1`（行为与 `0.3.0` 完全一致）。

### 兼容性与升级

- 声明范围未变：`>=0.1.7-rc.1 <0.2.0`（按 node-semver 预发布规则本就接纳 `0.1.7-rc.2`；刻意不放宽，以免额外接纳未测试版本）；
- **从 `0.3.0` 升级无需任何操作**：配置、密钥、设备配对与批准记录、CA 全部沿用；
- 回滚到 `0.3.0` 同样安全（代码与磁盘格式均未变）。

### 限制

- 与 `0.3.0` 相同：自签 CA 需每台设备信任一次；mDNS 默认关闭且手机浏览器基本用不上（二维码才是主路径）；远程默认只读；局域网明文 HTTP 需显式确认风险；访问密码是共享的；「永久拉黑」不依赖设备指纹，重新放行需管理员手动操作；不提供公网隧道 / IM Bot / 端口转发。

<h3 id="en-v0.3.1">English</h3>

### Version correspondence

Verified against **DeepSeek Harness `0.1.7-rc.2`** and still compatible with `0.1.7-rc.1`. The declared range is unchanged: `>=0.1.7-rc.1 <0.2.0`.

### Why this release exists

After DSH moved from `0.1.7-rc.1` to `0.1.7-rc.2` we walked the §8 checklist in `docs/RESEARCH.md` and concluded that **every host/client surface this plugin depends on is present and unchanged — no source change is required**. This is therefore a **verification release** (zero code change) that updates the compatibility metadata and documentation so npm users can see that the plugin is verified against rc.2.

### What changed

- `dsh.compatibility.dshReleases` gains **`0.1.7-rc.2: compatible`** (keeping `0.1.7-rc.1`);
- **Both READMEs' compatibility tables were rewritten**: they now carry the full `0.1.0 → 0.3.1` plugin-version ↔ DSH-version history, state the latest verified DSH version (**`0.1.7-rc.2`**), and explain how that verification was done (surface-by-surface check plus an end-to-end run);
- `docs/RESEARCH.md` gains §8.9 recording the rc.2 review;
- **No runtime code changed**: gate, proxy, self-signed TLS, device pairing and approval, settings UI and update detection are identical to `0.3.0`.

### Who is affected

- Anyone on **DSH `0.1.7-rc.2`**: the plugin is verified there, the interfaces did not change, and no configuration migration is needed;
- Anyone still on `0.1.7-rc.1`: **no upgrade required** — `0.3.0` keeps working;
- New installs: `@latest` resolves to `0.3.1` (behaviour identical to `0.3.0`).

### Compatibility and upgrading

- The declared range is unchanged: `>=0.1.7-rc.1 <0.2.0` (node-semver's prerelease rules already accept `0.1.7-rc.2`; widening it on purpose would only admit untested releases);
- **Upgrading from `0.3.0` needs no action**: configuration, secrets, device pairing/approval records and the CA all carry over;
- Rolling back to `0.3.0` is equally safe (neither the code nor the on-disk format changed).

### Limitations

- The same as `0.3.0`: the self-signed CA must be trusted once per device; mDNS is off by default and phone browsers rarely use it (the QR code is the reliable path); remote access is read-only by default; LAN plain HTTP requires an explicit risk acknowledgement; the access password is shared; the permanent ban does not use device fingerprinting, so re-admitting a device is a manual operator action; no public tunnels, IM bots or port forwarding.
