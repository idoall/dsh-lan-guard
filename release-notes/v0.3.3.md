<h3 id="cn-v0.3.3">中文</h3>

### 修复：失效的免密链接页，输不了密码

**症状**：扫码打开一条**已失效**的免密链接（被「重新生成」作废，或被截断丢了参数）时，页面正文写「请输入访问密码」，但密码框和提交按钮**都是灰的** —— 按提示去输密码却输不了，只能手动把地址里的 `?auth=…` 删掉才能重试，手机上很难操作。

**原因**：门禁把"链接失效"和"登录也没用"两类状态混在一起处理了。链接失效只说明**这条链接**不能用，密码登录仍然有效。

**现在**：该页面可以正常输入密码并进入。「未设访问密码」这类登录确实无用的状态，表单仍然禁用 —— 不给假希望。

### 修复：设备被移除后的提示是死路

被移除的设备页原先写「或让管理员删除该记录后重新确认」。但**删除记录并不能让它回来**：那台设备仍带着旧的身份 cookie，只会一直看到这一页。

**现在**改为：「请联系管理员在「已授权设备」中「解除拉黑」，同一台设备会立即恢复；若该记录已被删除，请清除本浏览器的本站数据后再访问。」——「解除拉黑」确实有效（保留记录，同一台设备立即恢复）。

### 变更：「拒绝并拉黑」的说明改为如实描述

设置页原先承诺：「拒绝并拉黑」会让设备"即使知道密码、换浏览器重新配对也被拒绝"。**实测并非如此**：拉黑后旧身份确实被拒（403），但同一台手机**清掉浏览器数据**（或换浏览器）后，用密码/免密链接可以重新配对并进入。

**现在**说明改成：拉黑作废的是**这台设备的身份** —— 它在这个浏览器里会被一直拒绝；清掉浏览器数据或换浏览器后仍可用密码重新配对。**要彻底挡住，请同时更换访问密码。**

（按 IP 兜底未实施：DHCP/VPN 会换 IP，可能误伤，留待评估。）

### 新增：首次访问的两道关，提前说明

门禁是两道关：**① 认证**（免密链接或访问密码）→ **② 给这台设备起名字**（配对）。设置页原先只写"扫码即登录"，让人以为一步到位。

**现在**：密码页在你提交**之前**就会提示「首次访问：通过后还需要给这台设备起个名字，方便你在「已授权设备」里识别和单独吊销。」；「扫码访问」tab 也补上"首次访问还要给这台设备命名一次，之后才不用再问"。若你关闭了「新设备需要命名确认」开关，这行提示不会出现（不承诺做不到的事）。

<h3 id="en-v0.3.3">English</h3>

### Fixed: an inert-link page you could not log in from

**Symptom**: opening a **dead** passwordless link (rotated with "regenerate", or truncated so the parameter was lost) showed a page saying "enter the access password" — while both the password field and the submit button were **disabled**. You could not type the password you were asked for, and had to edit `?auth=…` out of the URL by hand to retry.

**Cause**: the gate treated "the link is dead" and "logging in cannot help" as the same kind of state. A dead link only means **that link** is useless; the password still works.

**Now**: the page accepts the password and lets you in. States where logging in genuinely cannot help (no password configured) still disable the form — no promises it cannot keep.

### Fixed: the removed-device page pointed at a dead end

It used to say "or ask the operator to delete that record, then confirm again". But **deleting the record does not bring it back**: the device keeps presenting its old identity cookie and only ever sees this page.

**Now** it says: ask the operator to **「解除拉黑」(unblock)** — the same device is restored immediately; if the record was deleted, clear this browser's site data and visit again.

### Changed: the "block" description now matches real behaviour

The settings page promised that 「拒绝并拉黑」 kept a device out "even if it knows the password and re-pairs from another browser". **Measured, that is not what happens**: the old identity is refused (403), but the same phone — after clearing its browser data (or in another browser) — can pair again with the password/link and get in.

**Now** the note says what is true: blocking voids **this device's identity** — that browser stays refused, but clearing its data or switching browsers lets the password pair it again. **To truly shut it out, also change the access password.**

(An IP-based fallback is deliberately not implemented: DHCP/VPN change IPs and it could lock out the wrong device.)

### New: the two first-visit steps are announced up front

The gate has two steps: **① authenticate** (passwordless link or access password) → **② name this device** (pairing). The settings page only said "scan to log in", which read like a single step.

**Now** the password page says, before you submit: "first visit — after this you will also name this device, so you can recognise and revoke it individually". The access tab says the same. With the "new devices must be named" switch off, the hint does not appear — nothing is promised that will not happen.

### Verification

- both new test groups were **falsified**: reverting the fix fails the matching spec;
- `pnpm run build` passes; this release **changes no host/client interface** — only the plugin's own pages and copy.
