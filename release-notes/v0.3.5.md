<h3 id="cn-v0.3.5">中文</h3>

### 修复：用 `http://` 打开时，只看到「无法访问」而且日志里什么都没有

**症状**：把 `http://<地址>:<端口>` 交给浏览器（二维码或地址栏写成 http），页面显示「无法访问」，浏览器报 `ERR_EMPTY_RESPONSE`（-324），**日志里也没有任何记录**，完全看不出发生了什么。

**原因**：明文请求到达 TLS 端口时握手先失败，Node 默认**一个字节都不回**就断开；门禁在握手之后才运行，所以这一层失败在门禁侧完全不可见。

**现在**：这类请求会得到 **301 跳转到同地址的 `https://…/`**（浏览器自动切到正确协议），并留下 `tls handshake failed code=… plaintextHttp=… ip=…` 的日志。畸形请求同样会记录，并保持 Node 原本的 `400 Bad Request` 响应 —— 不会因为加了日志而把默认响应弄丢。真实的 TLS 客户端完全不受影响。

### 修复：删除设备记录后，这台浏览器被永久锁死

**症状**（手机实测）：一台曾经配对过的手机，在管理员**删除**它的设备记录后，永远只能看到「此设备已被移除访问权限」—— 换免密链接、输访问密码都进不去，只有清除本站数据才行。

**原因**：门禁把「带着设备 cookie、但记录已不存在」和「被吊销/拉黑」当成同一件事。而移除页在读取 `?auth=` **之前**就产生了，所以任何链接都救不回来。记录被删是**浏览器侧的过期状态**，不是身份。

**现在**：这种旧 cookie 被当作「没有 cookie」，直接走正常认证流程 —— 访问密码或新链接都能让这台设备重新进入（并拿到一条新身份）。**吊销与拉黑仍然拒绝**：它们的记录还在，语义没有变。

### 变更：移除页文案随之修正

「若该记录已被删除，请清除本浏览器的本站数据」这条死路已不存在，文案改为只保留真正有效的一条：请联系管理员在「已授权设备」中「解除拉黑」，同一台设备会立即恢复。

### 验证

- `pnpm run typecheck` ✓；`pnpm test` — **273 项全绿**（0.3.4 为 263 项，+10）；
- 新增的连接层用例用**真实 socket** 驱动监听器：明文请求必须拿到 301、真实 TLS 客户端不受影响、握手失败与畸形请求都要出现在日志里、畸形请求仍复现 Node 的 400；
- 门禁用例覆盖：旧 cookie 经免密链接与密码两条路都能恢复、WebSocket 升级不再 403、吊销与拉黑仍拒绝、移除页不再提「清除本站数据」；
- **反证**：在隔离副本里回退修复后重跑 —— 回退门禁修复会让 3 条恢复用例失败，回退连接层修复会让 3 条连接层用例失败，而固定「未改行为」的用例仍通过。

<h3 id="en-v0.3.5">English</h3>

### Fixed: an `http://` address showed a bare "can't reach this page", with nothing in the log

**Symptom**: handing the browser an `http://<address>:<port>` URL (a QR code or address bar written as http) produced a bare failure page with `ERR_EMPTY_RESPONSE` (-324) and **no log line at all**, leaving nothing to diagnose.

**Cause**: a plaintext request to the TLS port fails its handshake first, and Node's default behaviour is to answer **zero bytes** and drop the connection. The gate runs after the handshake, so this failure was invisible from the gate's side.

**Now**: such a request gets a **301 redirect to the same address over `https://…/`** (the browser switches protocol by itself) and a `tls handshake failed code=… plaintextHttp=… ip=…` log line. Malformed requests are logged too, while keeping Node's own `400 Bad Request` response — adding visibility never drops the default reply. Real TLS clients are completely unaffected.

### Fixed: deleting a device record locked that browser out for good

**Symptom** (measured on a phone): after an administrator **deleted** a paired phone's device record, that phone could only ever see "this device's access was removed" — neither a fresh passwordless link nor the access password helped; only clearing site data did.

**Cause**: the gate treated "carries a device cookie whose record no longer exists" exactly like "revoked/blocked". The removal page is produced **before** `?auth=` is ever read, so no link could rescue it. A deleted record is **stale browser state**, not an identity.

**Now**: such a cookie is treated as absent and the normal auth flow runs — the access password or a fresh link recovers the device (which then gets a new identity). **Revoking and blocking still refuse**: their records still exist, so their meaning is unchanged.

### Changed: the removal page copy follows the implementation

"if the record was deleted, clear this browser's site data" described a dead end that no longer exists. The notice now keeps only the advice that really works: ask the administrator to **解除拉黑** in 已授权设备 — the same device recovers immediately.

### Verification

- `pnpm run typecheck` passes; `pnpm test` — **273 passing** (263 in 0.3.4, +10);
- the new connection-level specs drive the listener with **real sockets**: a plaintext request must receive a 301, a real TLS client must be unaffected, handshake failures and malformed requests must appear in the log, and a malformed request must still reproduce Node's 400;
- the gate specs cover recovery through both the passwordless link and the password form, a websocket upgrade that is no longer refused, revoked/blocked records that are still refused, and the removal notice no longer mentioning site data;
- **falsified**: with the fixes reverted in an isolated copy, the gate revert fails 3 recovery specs and the proxy revert fails 3 connection-level specs, while the specs pinning unchanged behaviour keep passing.
